---
title: Properties and Consent
description: Store custom contact data and record SMS consent state correctly.
---

Contacts can carry application-specific properties and an explicit SMS consent state. Keep these fields accurate because audience and messaging workflows may rely on them later.

## Custom properties

Use `properties` for application data that does not belong in the built-in contact fields:

```json
{
  "properties": {
    "plan": "pro",
    "company": "Analytical Engines",
    "customer_id": "cust_42"
  }
}
```

Property keys cannot be empty. Dugble validates custom properties against the contact property definitions configured for the team, including expected types.

<Note>
When you update `properties`, send the complete property object you want stored. The update replaces the current object rather than merging individual keys automatically.
</Note>

## SMS consent status

Dugble supports three SMS consent states:

| State | Meaning |
| --- | --- |
| `unknown` | No explicit opt-in or opt-out state is recorded. |
| `opted_in` | The contact has explicit SMS consent. |
| `opted_out` | The contact has explicitly opted out of SMS. |

When `sms_consent_status` is `opted_in` or `opted_out`, include a consent source:

```json
{
  "sms_consent_status": "opted_in",
  "sms_consent_source": "api"
}
```

Supported sources are `api`, `import`, and `manual`.

## Changing consent

When updating a contact from one explicit consent state to another, provide a new `sms_consent_source` with the change.

```json
{
  "sms_consent_status": "opted_out",
  "sms_consent_source": "api"
}
```

Setting the state to `unknown` clears the stored consent source.

## Email unsubscribe state

The `unsubscribed` boolean is separate from SMS consent and from topic subscriptions. Use each field for its intended channel or preference layer rather than treating them as one global consent flag.
