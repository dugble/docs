---
title: Sending
description: Preview, send, schedule, cancel, and duplicate broadcasts.
---

Broadcast sending is built around a simple workflow: prepare the draft, preview the rendered content, then send now or schedule delivery for later.

## Prepare the draft

While a broadcast is in `draft`, you can change its name, segment, topic, template, and variable bindings.

Updates use the broadcast `revision` so concurrent changes do not silently overwrite each other. Once the broadcast leaves draft state, it can no longer be edited.

## Preview before sending

Preview renders the broadcast template with optional preview variables without sending any email.

Use preview to confirm the subject, HTML, text content, sender details, and variable rendering before the audience is processed.

<Note>
Previewing does not change the broadcast state and does not queue recipients.
</Note>

## Send now

A broadcast can only be sent from `draft`. The selected message template must have a published version.

When no future `scheduled_at` is supplied, Dugble queues the broadcast for asynchronous fanout. Recipient eligibility is applied before individual email messages are queued.

## Schedule a broadcast

Provide a future `scheduled_at` value to schedule the broadcast instead of sending immediately.

A scheduled broadcast remains cancelable until it begins queueing. Once processing starts, it can no longer be canceled through the scheduled-broadcast cancellation flow.

## Cancel a scheduled broadcast

Only broadcasts currently in `scheduled` state can be canceled. Canceling prevents the scheduled fanout from starting and moves the broadcast to `canceled`.

## Duplicate for reuse

Duplicating a broadcast creates a new draft based on an existing broadcast. This is useful when the audience, topic, template, or bindings are mostly the same but you want a separate send and lifecycle.

The duplicate receives its own name and can be edited independently before sending.

## After the send starts

Once queued, each eligible recipient has its own delivery lifecycle. Some recipients may queue successfully while others fail during fanout or later experience normal email delivery outcomes such as bounce or complaint.

Use the broadcast recipient list for per-recipient state and [Analytics](/broadcasts/analytics) for aggregate results.
