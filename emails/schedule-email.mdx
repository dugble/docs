---
title: "Schedule email"
description: "Send an email later, change its delivery time, or cancel it"
---

Set `scheduled_at` to queue an email for future delivery. Dugble stores the message immediately but does not make its delivery job available until the scheduled time.

## Schedule a message

For a new send, `scheduled_at` accepts an ISO 8601 timestamp or a relative value such as `in 5 min`:

```bash
curl --request POST \
  --url https://api.dugble.com/emails \
  --header "Authorization: Bearer $DUGBLE_TOKEN" \
  --header "Content-Type: application/json" \
  --header "Idempotency-Key: <unique-request-key>" \
  --data '{
    "to": "ada@example.com",
    "subject": "Your appointment is tomorrow",
    "text": "We will see you tomorrow at 10:00.",
    "scheduled_at": "2026-08-05T11:52:01.858Z"
  }'
```

Relative scheduling uses the time Dugble receives and validates the request:

```json
{
    "scheduled_at": "in 30 min"
}
```

Supported relative units include seconds, minutes, hours, and days. For predictable production workflows, prefer an explicit UTC ISO 8601 timestamp.

## Update the delivery time

Use `PATCH /emails/{message_id}` while the scheduled email is still queued. Updates require an ISO 8601 timestamp.

```bash
curl --request PATCH \
  --url https://api.dugble.com/emails/49a3999c-0ce1-4ea6-ab68-afcd6dc2e794 \
  --header "Authorization: Bearer $DUGBLE_TOKEN" \
  --header "Content-Type: application/json" \
  --header "Idempotency-Key: <unique-request-key>" \
  --data '{
    "scheduled_at": "2026-08-05T13:00:00Z"
  }'
```

```json
{
    "success": true,
    "data": {
        "object": "email",
        "id": "49a3999c-0ce1-4ea6-ab68-afcd6dc2e794"
    }
}
```

## Cancel a scheduled email

```bash
curl --request POST \
  --url https://api.dugble.com/emails/49a3999c-0ce1-4ea6-ab68-afcd6dc2e794/cancel \
  --header "Authorization: Bearer $DUGBLE_TOKEN" \
  --header "Idempotency-Key: <unique-request-key>"
```

Cancellation removes the pending delivery job and changes the message state to `canceled` in the same database transaction.

## Scheduling rules

- `scheduled_at` must resolve to a time in the future.
- A message can only be rescheduled or canceled while it is queued and scheduled.
- A message that is already processing or submitted cannot be changed or canceled.
- Use a unique `Idempotency-Key` for every distinct scheduling mutation.
- Retrieve the email after a mutation when your application needs to confirm its current state.

<Warning>
    Do not wait until the exact delivery time to reschedule or cancel a message.
    Network and queue processing can begin as soon as the scheduled time is
    reached.
</Warning>
